The six failures, and what causes them

F1 — LIMIT 50 reported as a count · Q9, Q16, Q18, Q19, Q29

Five of thirty-two answers. The worst case told the user there are 50 overdue invoices when there are 356,233.

QSaidActually
950 PR lines16,191
1650 open POs6,680 lines / 1,905 POs
1850 (implied)24,228 items / 5,546 POs
1950 invoices356,233 / 209,878 POs
2950 POs5,923 lines

Hard rule 2 says “always add LIMIT (50 unless asked for more)”. Trap 7 says “counts come from COUNT(*)”. The two rules sit in different sections and the agent follows the first and forgets the second. Q19's hedge — “50 invoices that are overdue (and possibly more)” — shows it half-knew.

Proposed fix. Merge the two rules into one instruction at the point of use: any question phrased as which / how many / is there anything takes two queries — a COUNT(*) with no LIMIT for the headline, then a LIMIT 50 sample for the table. State the real total in the first sentence and label the table “showing the oldest 50 of N”.

F2 — Max iterations, caused by guessed column names · Q27, Q30

Confirmed from the n8n execution trace (execution 25433). The agent's ten iterations on Q30 went:

#What it didResult
1SELECT pr_num … request_lifecyclecolumn "pr_num" does not exist
2SELECT pr_num … pr_waiting_withsame error
3SELECT po_num … po_waiting_withcolumn "po_num" does not exist
4SELECT po_num … goods_receiptsame error
5SELECT po_num … invoicesame error
6information_schema for request_lifecyclecolumn list
7the actual answercorrect rows
8information_schema for goods_receiptcolumn list
9GRN querycorrect rows
10information_schema for invoicelimit reached

Five of ten iterations were spent guessing pr_num and po_num when the columns are pr_number and po_number. Another four were information_schema round-trips. One iteration out of ten did real work.

The prompt lists all sixteen views and their grain, but not a single column name — it tells the agent to go and look them up. At ten iterations, that budget does not survive a question that touches four views.

Proposed fix, in order of effort:

  1. Put the key columns in the prompt: every view keys on pr_number, pr_item, po_number, po_item — never pr_num or po_num. One line would have saved five iterations.
  2. Add a compact column dictionary for the six most-used views, so information_schema is a fallback rather than the first step.
  3. Raise max iterations from 10 to 15.

(1) and (2) are the real fix; (3) alone would just let it waste more.

F3 — Zero rows arrives as [{"success":true}]

Visible in the same trace. SELECT … FROM track.pr_waiting_with WHERE pr_number = '1005026000' correctly matched nothing — the PR is fully released — and the tool returned [{"success":true}], not an empty array.

Nothing in the prompt says what that means. The agent treated it as an anomaly and spent a further iteration probing. An empty result that does not look empty is exactly the shape of error that produces a confidently wrong answer — this is the same class of problem as the \m/\M escapes, which also returned zero rows silently.

Proposed fix. One line in the Traps section: [{"success":true}] from query_track_db means the query ran and matched zero rows. It is an empty result, not an error — go to Trap 1.

F4 — Presentation · Q6

Twelve identical rows, and raw column names as headers. Both are already covered by the prompt; the instruction is just buried mid-section. Worth moving the “say it once” rule into the hard rules and adding “table headers are readable English, never raw column names.”

F5 — Negative invoice balances · Q17, Q19

As above. Either document the sign convention in col_comments so the agent can explain it, or wrap invoice_balance in the track.invoice view. I lean towards documenting it — flipping the sign would diverge from what the source model and SAP both show, and anyone cross-checking would be confused.

F6 — Receipt column on an unapproved PO · Q3

A single instance, and the mildest finding. The rule exists; the agent applied it on Q6 and Q7 but not on the general-status question. Probably needs the rule restated for the “what's happening with” case specifically.

What is working

Worth stating plainly, because it is most of the run:

  • All six trap questions passed. The service-line trap, the DHL supplier trap, and three separate “we do not have that data” questions were all answered correctly, including volunteering the limitation rather than guessing.
  • Every aggregate that used COUNT(*) was exact. Q11, Q28 and Q32 match ground truth to the row. The data layer is sound; the failures are in how results are summarised, not in what is retrieved.
  • The agent discloses its method. Q22 stated the filter it used unprompted, which is what makes a wrong filter visible instead of hidden.
  • It asks instead of assuming. Q4 and Q26 both stopped and asked for an identifier rather than inventing a scope.
  • Response times are usable. Median 31s, and the two slowest (83s, 61s) were both large unbounded-looking list questions — which F1 would also make faster, since a COUNT(*) plus 50 rows beats dragging 50 wide rows back for the model to reason over.

Recommended order of work

Nothing here has been changed yet — this is the report, as asked.

  1. F1 — the count rule. Five questions, one of them off by a factor of 7,000. Highest value, lowest risk, prompt-only.
  2. F2 — key column names plus a short column dictionary in the prompt. Turns two hard failures into answers.
  3. F3 — one line documenting [{"success":true}]. Cheap, and it closes a silent-wrong-answer path.
  4. F5 — document the invoice_balance sign convention in col_comments.
  5. F4 / F6 — presentation rules, promoted into the hard rules.

F1–F4 are all edits to the Track My Request system prompt. F5 is a col_comments edit, which flows through /admin/columns and survives every swap. No schema or view changes are needed for any of this.

Re-running this same 32-question set after the changes gives a direct before-and-after, since eval/ground_truth.json is already measured.
