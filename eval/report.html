The six failures, and what causes them

F1 — LIMIT 50 reported as a count · Q9, Q16, Q18, Q19, Q29

Five of thirty-two answers. The worst case told the user there are 50 overdue invoices when there are 356,233.

QSaidActually
950 PR lines16,191
1650 open POs6,680 lines / 1,905 POs
1850 (implied)24,228 items / 5,546 POs
1950 invoices356,233 / 209,878 POs
2950 POs5,923 lines

Hard rule 2 says “always add LIMIT (50 unless asked for more)”. Trap 7 says “counts come from COUNT(*)”. The two rules sit in different sections and the agent follows the first and forgets the second. Q19's hedge — “50 invoices that are overdue (and possibly more)” — shows it half-knew.

Proposed fix. Merge the two rules into one instruction at the point of use: any question phrased as which / how many / is there anything takes two queries — a COUNT(*) with no LIMIT for the headline, then a LIMIT 50 sample for the table. State the real total in the first sentence and label the table “showing the oldest 50 of N”.

F2 — Max iterations, caused by guessed column names · Q27, Q30

Confirmed from the n8n execution trace (execution 25433). The agent's ten iterations on Q30 went:

#What it didResult
1SELECT pr_num … request_lifecyclecolumn "pr_num" does not exist

10information_schema for invoicelimit reached

Five of ten iterations were spent guessing pr_num and po_num when the columns are pr_number and po_number. Another four were information_schema round-trips. One iteration out of ten did real work.

The prompt lists all sixteen views and their grain, but not a single column name — it tells the agent to go and look them up. At ten iterations, that budget does not survive a question that touches four views.

Proposed fix, in order of effort:

  1. Put the key columns in the prompt: every view keys on pr_number, pr_item, po_number, po_item — never pr_num or po_num. One line would have saved five iterations.
  2. Add a compact column dictionary for the six most-used views, so information_schema is a fallback rather than the first step.
  3. Raise max iterations from 10 to 15.

(1) and (2) are the real fix; (3) alone would just let it waste more.

F3 — Zero rows arrives as [{"success":true}]

Visible in the same trace. SELECT … FROM track.pr_waiting_with WHERE pr_number = '1005026000' correctly matched nothing — the PR is fully released — and the tool returned [{"success":true}], not an empty array.

Nothing in the prompt says what that means. The agent treated it as an anomaly and spent a further iteration probing. An empty result that does not look empty is exactly the shape of error that produces a confidently wrong answer — this is the same class of problem as the \m/\M escapes, which also returned zero rows silently.

Proposed fix. One line in the Traps section: [{"success":true}] from query_track_db means the query ran and matched zero rows. It is an empty result, not an error — go to Trap 1.

F4 — Presentation · Q6

Twelve identical rows, and raw column names as headers. Both are already covered by the prompt; the instruction is just buried mid-section. Worth moving the “say it once” rule into the hard rules and adding “table headers are readable English, never raw column names.”

F5 — Negative invoice balances · Q17, Q19

As above. Either document the sign convention in col_comments so the agent can explain it, or wrap invoice_balance in the track.invoice view. I lean towards documenting it — flipping the sign would diverge from what the source model and SAP both show, and anyone cross-checking would be confused.

F6 — Receipt column on an unapproved PO · Q3

A single instance, and the mildest finding. The rule exists; the agent applied it on Q6 and Q7 but not on the general-status question. Probably needs the rule restated for the “what's happening with” case specifically.

What is working

Worth stating plainly, because it is most of the run:

  • All six trap questions passed. The service-line trap, the DHL supplier trap, and three separate “we do not have that data” questions were all answered correctly, including volunteering the limitation rather than guessing.
  • Every aggregate that used COUNT(*) was exact. Q11, Q28 and Q32 match ground truth to the row. The data layer is sound; the failures are in how results are summarised, not in what is retrieved.
  • The agent discloses its method. Q22 stated the filter it used unprompted, which is what makes a wrong filter visible instead of hidden.
  • It asks instead of assuming. Q4 and Q26 both stopped and asked for an identifier rather than inventing a scope.
  • Response times are usable. Median 31s, and the two slowest (83s, 61s) were both large unbounded-looking list questions — which F1 would also make faster, since a COUNT(*) plus 50 rows beats dragging 50 wide rows back for the model to reason over.

Update — fixes applied and retested

F1 to F4 went into the Track My Request system prompt, plus the piece that made F2 worth doing properly: the agent now has an editable column dictionary over the schema it actually reads.

The gap F2 exposed was bigger than the fix. /admin/columns documented 472 columns on core.* — but Track My Request reads track.* and is forbidden from querying core.*, and the views rename columns on the way through. Measured before any of this: 16 views, 444 columns, 0 commented. The agent had no column context at all, which is exactly why it was guessing names and burning iterations on information_schema.

Three pieces, so the content is yours to edit rather than buried in n8n:

  • ai.column_docs holds the descriptions as data — the same shape the other three databases already use, so the admin API needed no changes.
  • core.rebuild_track_views() replays them as Postgres COMMENTs after each view is recreated. Without this, every nightly publish_all would wipe them, because a dropped view takes its COMMENTs with it.
  • track.column_guide exposes the whole dictionary in one query, replacing the per-view lookups.

449 of 449 columns are now documented, verified to survive a full drop-and-rebuild, and editable at /admin/columns → Track My Request. A save writes the data and re-applies the COMMENT in the same transaction, so an edit is live for the agent on its very next query.

Cancelled requisitions counted as stuck. That is worse than the original “50”, because it is wrong and confident. Real answer: 5,841.

F8 — a new finding: buyer reported as approver

Q3 and Q7 now say the order is sitting with “buyer Bashar Al Arar (ID 0064)”. Those are two different people: 0064 is the approver; Bashar Al Arar is the buyer who raised the order. Telling someone to chase the buyer sends them to the wrong desk, which is the specific failure these two questions exist to catch.

The column description already warns about it in as many words — “This is who raised the order, NOT the approver holding it” — and the agent conflated them anyway. So this one probably needs the data to stop making it easy: either drop buyer_name from approval-shaped answers, or resolve waiting_with to a name so there is a right name to reach for. Not yet fixed.

Second round — F5, F6 and F8

F5 was not a display problem. It was a correctness bug. Measuring the column before changing anything turned up something the original report had missed entirely.

Over all 373,820 loaded invoices:

  • invoice_balance equals -invoice_amount on all 372,631 non-zero rows. The minus sign is pure credit-side bookkeeping convention and carries no information at all.
  • payment_amount is non-zero on only 3,865 of 373,820 rows — and on every one of those it equals invoice_amount to the cent. It mirrors the amount. It never records a part payment.

So the view’s own payment_state was labelling those 3,865 rows “Partially paid” when nothing had been paid at all. The state is now removed — the source cannot express partial payment — and amount_outstanding added as the plain positive figure to report. invoice_balance is kept exactly as the source has it, so it still reconciles against SAP and the AP Aging model; flipping its sign would have made this view disagree with every other system showing the same number.

A third max-iterations failure, with a new cause

Q3 died on the first F5/F6 retest. The trace shows a different problem from Q27 and Q30: 6 of 9 iterations were lost to single wrong column names — po_number on request_lifecycle (it is po_numbers, plural), unit (it is order_unit), requisitioner_name, and buyer_name and waiting_with on po_line, where neither exists.

The database reports only ONE missing column per attempt. So a wide hand-written SELECT costs an iteration per wrong guess, and six guesses eat a ten-iteration budget before the real question is reached. The column guide did not help here, because the agent was writing the column list from memory rather than checking it.

Fix: for a single named document, SELECT * and pick from what comes back. No enumeration, no guessing, one iteration. That is also why the retest times dropped — Q12 went from 26s to 9s.

F8 closed as a side effect

Q3 now reads: sitting with approver 0064, raised by buyer Bashar Al Arar — two people, correctly separated. The clearer column handling fixed it without needing the view change the first report proposed.

One fabricated number, caught

On the first F5 retest Q17 said the invoice was “overdue for 53 days”. The real figure is 317, and 53 appears in no column anywhere — it was invented. Checking further, days_past_due is computed when the source model is built and disagrees with CURRENT_DATE on all 373,820 rows, usually by a day. That is now documented, and the rule against unverified arithmetic tightened to cover any stated number. Q17 reads 317 correctly after the change.
